# Suggestions: formalising and improving the platform

*Written 2026-11-15 at Lokesh's request, after the platform refactor (SDK v2,
one-page shell). Ordered by value per effort within each group. None of
this is built unless a section says so.*

## 1. Make the contract formal

- **Version the protocol properly.** `protocol.json` carries its version
  (`2`) on every message. Add a written policy:
  - additive changes (new optional fields or messages) keep 2.x;
  - a breaking change is v3, accepted beside v2 for a stated window.
  - Keep a `CHANGELOG.md` for the SDK, with dates.
- **Publish the SDK as packages.** The adapters are folders to copy today.
  Publish `@arcade/runtime` and `@arcade/ts` on npm, the `arcade` crate on
  crates.io, a Go module tag (`sdk/v2/adapters/go/v2.x.y`) and a Python
  wheel, so authors depend on a version instead of a copy.
- **A scaffold command.** `npm create arcade-game` asks for a language and
  a lane, then writes a working managed Tic Tac Toe from the examples,
  with its build script, RULES.md and game.json.
- **A conformance kit for authors.** `just test-conformance` proves our
  examples. A packaged `arcade-check` would let authors run validate-game,
  a bots-only fuzz play to the end, and a protocol trace check before they
  open a pull request, and CI would run the same thing.
- **A manifest JSON Schema** (`game.schema.json`) beside protocol.json, so
  editors autocomplete `game.json` and the PR check reports by field.

## 2. Contributor experience

- **The submission report** already comments on the PR (submission-report).
  It should also include a screenshot at 390×844 and a short clip, so
  review needs no checkout.
- **Preview media generated by CI.** The preview clip should be recorded on
  submission (scripts/preview.mjs) rather than asked of authors.
- **Per-game analytics for authors:** plays, finish rate, average match
  length and the share played with bots, shown on their Contributors card
  (from the play counts the worker already keeps).
- **Feedback routed to the author's repo**, as issues (the feedback API
  already posts to GitHub).

## 3. Quality bars, automated

- **Bots-only fuzz on every PR:** play each managed game to a result with
  `bot()` on every seat, many seeds, failing on a stall or a throw. The
  rules are pure functions, so this is cheap.
- **Performance budgets** per game: first view in under N ms at 4× CPU,
  memory ceiling, no long tasks over 200 ms. Measured by perf.mjs's frame
  throttle and enforced in the PR check.
- **Accessibility checks:** contrast from theme tokens, tap targets ≥ 44
  px, a keyboard path through the board, `prefers-reduced-motion`.
- **A real-device run before each release:** the gaps so far (DPR-3 fill
  cost, iOS Safari, video previews failing in headless) are all device
  questions.

## 4. Trust and fairness

- **Score verification, done in steps.** Server-issued runs and Sudoku
  verification are being built this round. Next, **replay verification**
  for real-time games: seeded randomness in the managed rules, the input
  log submitted with the result, and the Worker re-running the same rules
  (JS, or the WASM module) and accepting only the score it computes.
  Scores verified that way get a "verified" mark; unverified solo scores
  sit apart.
- **Moderation:** player names and chat (Draw & Guess guesses) need a word
  filter and a report button, with reports going to the feedback queue.
- **Content policy and licences:** a short policy for submitted games
  (content, no tracking, assets licensed), checked at submission.

## 5. Players

- **A daily challenge.** One seeded puzzle or run per day, the same for
  everyone, with its own leaderboard. It reuses server-issued runs and
  replay verification, so it is cheap once those exist.
- **Achievements and profiles:** per-game achievements declared in
  game.json and checked from `result().details`, shown on profiles.
- **Tournaments and parties over time:** a group's season (the groups
  exist), best of N series (the end card's series tally is a start), and a
  bracket view.
- **Spectating and replays:** a spectator seat already exists. A replay
  could be the view stream recorded, shareable as a link.
- **Async turn-based play:** a turn game that waits for days, with the room
  server keeping the snapshot. This needs storage per party, and is a
  larger change.
- **i18n:** the shell's strings in one table, with games' RULES.md per
  language (`RULES.<lang>.md`).

## 6. Engineering and operations

- **Deploy the Worker from CI** with an approval step, and a staging Worker
  for previews. Today it is a manual `wrangler deploy`, separate from the
  site.
- **D1 backups and migrations in CI:** apply `worker/migrations` with a
  check that they are additive, and run nightly exports.
- **Error reporting (opt-in):** uncaught errors in the shell and in game
  frames, sent with the feedback mechanism, rate-limited, with no personal
  data.
- **Finish the Solid migration.** The party and lobby screens (lib/party.js,
  lib/lobby.js) are the last vanilla UI. Converting them lets the party
  screen share components with the views.
- **A pinned toolchain:** one `flake.nix` dev shell with pnpm, Node, Rust
  and wasm-bindgen, Emscripten, TinyGo and wrangler at fixed versions,
  replacing the floating `nix shell nixpkgs#…` calls.
- **A cache for Pyodide across deploys:** today it lives in each deploy's
  snapshot and is fetched again (12.8 MB) after every deploy. It should get
  a long-lived cache keyed to its version.
